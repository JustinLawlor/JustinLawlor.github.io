Overview

The problem

XYZ Health Solutions ran patient records, appointment scheduling and billing in three separate systems. Staff re-entered data by hand, errors slipped through, nobody had a real-time view of the patient, and the scattered data created HIPAA risk. The goal was one integrated platform on MySQL with a data warehouse and dashboards, under HIPAA governance.

The main stakeholders were the CEO (project sponsor), the project lead, the IT director, clinical operations, patient services, a data analyst, and the patients themselves.

Step 1

Requirements gathering and planning

I planned four ways to gather requirements: patient surveys, clinician workshops, admin interviews and IT technical workshops. From there I wrote:

  • A project charter, stakeholder register and engagement plan
  • A business requirements document with 5 functional and 3 non-functional requirements
  • A requirements traceability matrix linking each requirement to its objective, owner, risk, verification method and test case
  • A WBS (3 phases, 9 work packages), a network diagram with a critical path of about 7 months, a SWOT analysis, and a risk register scored by probability times impact
Step 2

Process and system design

I started with a use case diagram to agree on who uses the system and for what: five actors and nine use cases, from booking an appointment to maintaining security.

I mapped the core process, appointment scheduling, as a swimlane flowchart across Patient Services, the Clinical Department and the Scheduling System. It has five decision points, with loops for a failed login, an unavailable slot, missing fields, invalid input and a failed confirmation.

To show how data moves, I drew a context diagram with the whole system as one process, then broke it into a Level 1 data flow diagram.

Finally, a sequence diagram for booking an appointment shows the order of calls between the patient, the system, the appointment store and the payment gateway.

Step 3

Data design

The database has five tables: Patient, Staff, Appointment, Medical Record and Billing, documented in a 24-field data dictionary. I modelled them in two steps: a conceptual ERD with just the entities and relationships, then a logical ERD with keys and attributes.

The key design decision was taking PatientID out of Billing. The patient can already be found through the appointment (BillingID to AppointmentID to PatientID), so keeping it was a transitive dependency. I made AppointmentID unique in Billing to keep one bill per appointment, which brought the design to 3NF. CHECK constraints block negative amounts and invalid status values.

TableColumnTypeConstraints
AppointmentAppointmentIDINTPK, NOT NULL, AUTO_INCREMENT
AppointmentPatientIDINTFK to Patient, NOT NULL
AppointmentStatusVARCHAR(20)CHECK IN ('Scheduled','Completed','Cancelled','No-show')
BillingBillingIDINTPK, NOT NULL, AUTO_INCREMENT
BillingAppointmentIDINTFK to Appointment, UNIQUE, NOT NULL
BillingAmountDECIMAL(10,2)NOT NULL, CHECK (Amount >= 0)
BillingPaymentStatusVARCHAR(20)CHECK IN ('Pending','Paid','Overdue')
Step 4

Data analysis

I cleaned 20-record patient and appointment datasets in Excel (duplicates, missing values, date formats, location names) and added age and month fields. Then I built PivotTable charts and Power BI dashboards. Some findings:

  • 20% of patient records were missing an email address and 2 were missing a date of birth
  • $135,900 was outstanding, 77% of it on individual accounts
  • 55% of patients were in the US, and the New York clinic brought in 39% of recorded revenue
Step 5

Testing

I reviewed a draft test plan for the booking requirement (REQ-APPT-01), added missing preconditions, and wrote four new test cases: invalid login, duplicate booking, unauthenticated access and session timeout. I also changed the error messages to a generic "Invalid PatientID or credentials." so the system never reveals which patient IDs exist.

TDD objective: block a PatientID after three failed booking attempts in a row, reject a fourth request during the lockout even with correct credentials, and write the attempt to the audit log.

Scenario: Booking is rejected for a PatientID that is not registered
  Given no patient account exists for PatientID "P99999"
  When a user enters PatientID "P99999" and any credentials
  And clicks "Book"
  Then the booking is rejected
  And the error "Invalid PatientID or credentials." is displayed
  And no patient data is shown
  And the failed attempt is recorded in the audit log

Edge cases I flagged: picking an unavailable slot should not count as a failed attempt, the failed-attempt count has to be stored on the server so a page refresh can't reset it, and the booking page needs rate limiting against bots.

Step 6

Validation

The final presentation was peer-reviewed against a published rubric. Before submitting, I checked the deck against that rubric and added what was missing: the full traceability matrix columns, risk register fields, test case traceability and edge cases. User acceptance testing with clinic staff is part of the release plan below but was not performed, since this was a course project.

Step 7

Deployment and monitoring plan

I designed a 9-stage release pipeline from code commit to post-deployment checks, with automated stages in Jenkins or GitHub Actions and six checkpoints where an analyst reviews the work: requirement check, test results, logs and error messages, UAT sign-off, go/no-go, and the first 24 hours after release.

The monitoring plan defines seven metrics with thresholds: uptime, booking error rate, unauthorized access attempts, lockouts, response time, double bookings and audit log health. Alerts would go through Datadog, Slack, PagerDuty and Jira, with a daily, weekly and monthly maintenance checklist and a four-level incident severity workflow. All of this is planned, not running.

Outcome

Results

The project produced a full analysis package: charter, BRD, traceability matrix, risk register, process and data models, a test plan and a release plan. The project's targets were 100% HIPAA compliance, 20% fewer scheduling errors, 25% fewer data-entry errors and a 10% rise in patient satisfaction within 12 months. These are targets set in the plan, not measured results.

What I learned

  • Check the math in templates. The risk scores had been added instead of multiplied. Fixing it moved two risks onto the urgent list.
  • Write the test before the logic. Writing the lockout tests first, test-driven development style, surfaced the edge cases before any code existed: a slot error shouldn't count as a failed attempt, the attempt counter has to live on the server, and bots need rate limiting.
  • Security shows up in small details. A generic error message is what stops the system from revealing which patient IDs exist.
